# Sion 数据采集与评测记录（2026-09-03）

## 1. 评测目标

本轮验证 Sion 作为“主动式、可学习且可控的桌面伙伴”所需的三类能力：

1. 对话执行质量：严格指令、不确定性表达、跨主题隔离、短期上下文、结构化输出；
2. 用户边界：明确禁止长期记忆时不应落库，明确禁止工具调用时不应执行工具；
3. 可观测性：记录端到端延迟、LLM 调用与 Token 开销、主动决策漏斗、进程健康和记忆库变化。

本轮使用本地 Dashboard 与实际 DeepSeek Provider。所有测试消息均带 `【评测】` 标识；结果只能作为工程验证，不能代替长期真实用户实验。

## 7. 本轮发现的主要问题

### P0：记忆提取重复处理历史窗口

测试开始前 Dashboard 显示 48 条事实，结束后为 73 条，其中 61 条仍为待确认。新增条目主要来自对既有 50 条对话窗口的再次提取，而非 7 条新测试消息。事实库中存在 9 条精确重复行：

- “正在开发名为 Aurora 的 Go 电商项目”出现 5 次；
- “Aurora 项目的核心目标是保证下单与库存的一致性”出现 4 次；
- 另有饮品偏好和项目描述的重复组。

精确重复至少占 `9/73 = 12.3%`，尚未计入措辞不同但语义相同的重复。说明当前异步 MemoryWorker 会重复扫描历史窗口，缺少已处理游标、来源消息 ID 或可靠的语义 upsert。它会造成记忆膨胀、召回偏置和额外 Token 开销，应优先修复。

积极结果是：明确标记为虚构并禁止长期记忆的 `ZEPHYR-931` 未出现在事实库中，说明本轮记忆边界场景通过。

### P1：成本观测粒度不足（已修复）

7 轮交互产生 24 条统一标记为 `chat` 的 LLM 调用记录，最初无法区分主回复、情绪评估、事实提取和主动后处理各自成本。现已通过请求上下文完成分类，并让记忆任务复用统一限流与 Provider 路由；验收见第 11 节。

### P1：主动策略缺少真实样本

30 次机会中只有 1 次投递和 1 条反馈；影子策略 23 次比较均未产生分歧，也没有匹配回放反馈。当前不足以评价规则策略与 Bandit 的优劣。

### P2：决策快照一致性检查

部分决策快照中的 `e6_llm_available=false` 与健康接口 `llm=ok` 同时存在。需要确认该字段表示瞬时可用性、是否在决策时未注入，或是否存在健康状态同步问题。

## 8. 下一轮建议

1. 为 MemoryWorker 增加来源消息游标和事实幂等键，复跑同一历史窗口时新增事实应为 0；
2. 将 TokenTracker 的 `call_type` 拆成 `chat_response / emotion_eval / fact_extract / post_chat / system2`；
3. 增加 TTFT、完整响应耗时和错误码指标，固定回归集至少重复 5 次；
4. 进入 2—4 周真实使用期，仅由用户本人提交显式反馈，累计至少 50 条后再评价上下文偏好与影子策略；
5. 每周输出按动作、时段和工作状态分桶的有帮助率、负反馈率及 `bad_timing / irrelevant / wrong_tone` 分布。

## 9. 当前可用于简历的结论边界

可以写：实现了可审计的主动决策与显式反馈闭环；7 类固定对话回归场景通过；本轮 `n=7` 的完整响应 P50 为 2.39 秒、P95 为 3.05 秒。

暂时不能写：主动消息满意度提升、Bandit 优于规则策略、记忆召回准确率提升或长期资源占用稳定。这些结论仍缺真实样本或对照实验。

## 10. P0 修复与验收

本轮评测后已经完成第一阶段修复：

- 使用 SQLite 持久化 `fact_extraction_message_id`，MemoryWorker 只读取游标之后的新消息；
- 首次升级时将游标初始化到既有消息尾部，避免部署后重新提取全部旧历史；
- 为事实增加 `fact_sources` 来源关联表，可追溯到参与该批提取的消息；
- 写入前按照规范化 `entity + relation_type + content` 做精确幂等，重复事实关联新来源而不新增事实行；
- 对包含明确禁止记忆指令的轮次写入 `memory_policy=ephemeral`，事实提取前程序级过滤用户消息和对应回复；
- 增加增量批次、重复事实、临时消息、重启游标和旧库升级五类自动化断言，并通过 race detector、全量测试和 `go vet`。

真实运行验收结果：升级后消息表尾部 ID 为 79，提取游标同为 79；发送包含临时代号 `CURSOR-482` 且明确禁止长期记忆的完整对话后，事实总数保持 73，事实库中该代号命中数为 0，旧 50 条历史没有再次提取。

现有 73 条事实中的历史重复暂未自动删除，以避免破坏用户数据。后续需要独立的可预览迁移工具完成旧数据清理；语义近似但文本不同的事实合并已在第 12 节完成，并只阻止后续继续膨胀。

## 11. 调用归因与对话链路优化

本轮继续完成成本可观测性与普通对话调用放大治理：

- 通过请求上下文携带 `route` 与 `call_type`，共享执行器仍可按任务选择 Provider；
- Token 记录拆分为 `chat_response`、`emotion_eval`、`fact_extract`、`memory_signal`、`reflection_diary`、`memory_summary`、`post_chat_decision`、`system2_decision` 等稳定类别；
- Memory LLM Hooks 改为复用全局受限流、受追踪的执行器，消除记忆调用绕过全局 20 calls/min 限制及成本漏记的问题；
- 删除普通聊天前单独执行的 LLM 工具频道分类。当前仅 7 个内置工具，直接交给主模型的 function calling 判断即可，避免一次串行 API 请求，同时保持工具能力；
- 增加“上下文覆盖调用类型”“上下文覆盖 Provider 路由”“无元数据回退默认值”“工具对话只发起一次主模型调用”等回归测试。

真实对照验收使用两条等价的临时消息，均只生成指定确认文本且未写入长期记忆：

| 版本 | 同步调用分类 | 完整响应耗时 | Prompt Tokens（同步链路） |
|---|---|---:|---:|
| 优化前 | `emotion_eval + chat_route + chat_response` | 1.92 s | 1,259 |
| 优化后 | `emotion_eval + chat_response` | 2.14 s | 1,052 |

优化后确定减少 **1 次串行 LLM 调用**及约 **207 Prompt Tokens（16.4%）**。两次耗时样本受 Provider 波动影响，不能据此宣称延迟下降；后续应对同一固定提示重复至少 20 次，并单独记录 TTFT、完整响应时间及各调用阶段耗时。

## 12. 语义合并与本地 Embedding 接线

在规范化精确幂等之上增加两阶段保守合并：

1. 仅在相同 `entity + relation_type` 桶内比较，先用中文/英文字符二元片段计算词面语义相似度；
2. 词面未命中时，使用本机 Ollama 的 `bge-small-zh-v1.5` 生成 512 维向量，余弦相似度达到 0.93 才允许合并；
3. 极性不同、数字不同或长度差异过大的事实直接禁止自动合并，避免把“喜欢/不喜欢”和版本号、数量变化错误折叠；
4. 合并不会静默丢弃内容：`fact_merge_audit` 保存目标事实、原始输入、原因和相似度，`fact_sources` 继承新来源消息；
5. 服务启动后异步回填旧事实缺失或模型版本不一致的向量；Ollama 不可用时退化为规范化文本路径。

本机模型校准结果：近义改写“正在开发一个名为 Aurora 的 Go 电商项目”与“正在开发名为 Aurora 的 Go 电商项目”余弦相似度为 **0.988**；不同偏好对象“喜欢茉莉花茶”与“喜欢咖啡”为 **0.696**；相反极性样本为 **0.881**，同时会被极性硬门槛拦截。自动化测试覆盖同义改写、相反偏好、不同数字、向量路径、审计记录、来源继承和旧事实向量回填。

最终构建产物启动验收：运行时正确加载本地 BGE 模型，异步回填日志显示 `updated=73 total=73`；数据库核验 73 条活跃事实均已写入向量及模型标识。

现有历史重复仍未自动删除；本次机制负责阻止后续继续膨胀。历史清理应另做可预览、可回滚迁移，不能直接批量删除用户数据。

## 13. 两组各 20 轮固定对照测试

测试消息均声明为虚构临时数据，并要求只输出唯一确认码；两组均为 **20/20 通过**。TTFT 定义为请求开始至首段可见回复；当前工具模式为完整生成后伪流式，因此 TTFT 接近完整生成时间。

| 指标 | 优化前（情绪 LLM 每轮调用） | 优化后（中性请求规则门控） | 变化 |
|---|---:|---:|---:|
| 平均情绪评估 | 3,010.77 ms | 0.05 ms | -99.998% |
| 平均记忆召回 | 7.70 ms | 71.30 ms | 本地 BGE 接入；首轮冷启动 718.77 ms |
| 平均主生成 | 2,408.71 ms | 2,539.63 ms | Provider 波动范围内 |
| 平均 TTFT | 5,711.08 ms | 2,897.95 ms | **-49.3%** |
| TTFT P50 | 5,975.81 ms | 2,847.52 ms | **-52.3%** |
| TTFT P95（nearest-rank） | 8,953.53 ms | 6,003.98 ms | **-32.9%** |
| 平均完整响应 | 5,713.60 ms | 2,900.12 ms | **-49.2%** |

Token 分类结论：

- 优化前 20 轮中，`emotion_eval` 共 20 次、15,077 Tokens，占窗口总 Token 的 52.3%；
- 优化后中性请求不触发 `emotion_eval`，同步对话 Token（情绪评估 + 主回复）由 27,679 降至 13,880，下降 **49.9%**；
- 包含反思、摘要、System 2 和 post-chat 后处理的窗口总 Token 从 28,846 降至 17,914，下降 **37.9%**；
- `post_chat_decision` 两组均只触发 1 次，优化后为 235 Tokens。现有两分钟门控已经有效降频，占比很低，暂不切换模型；继续保留真实使用反馈后再决定。

基于数据采取的策略：技术问答、格式指令和中性命令走确定性情绪规则；出现焦虑、难过、愤怒、喜欢、陪伴等情绪或关系信号时仍调用 LLM。这样减少常规链路成本，同时不牺牲情绪场景的细粒度判断。
